계약과 실제 운영이 시작되기 전까지 매달 코드 전체를 점검합니다. 버그·보안·결제 문제와 운영 방식, UI/UX, 문구 톤까지 함께 봅니다. 꼭 고쳐야 하는 건 점검하면서 바로 고쳐 데모(프리뷰)에 올리고, 사용자가 정해야 하는 것만 "결정 필요"로 남겨 둘게요.

점검 기록

예약 점검은 매달 첫째 주 화요일 오전 9시 43분(한국 시간)에 실행됩니다. 결과는 회차마다 한 줄씩 남기고, 새로 찾은 항목은 위 표에 이어 붙입니다. 첫 월간 회차는 사용자가 요청할 때 직접 돌려요.

운영 방식

2026-11-24에 정한 규칙입니다. 질문을 누르면 답이 펼쳐져요.

무엇을 점검하나?

4갈래를 따로 조사한 뒤, 찾은 것은 코드로 한 번 더 확인합니다. ① 결제·정산·환불(구글·애플 구독, 창립 파트너 배분, 갈아타기) ② 메시지·보안·개인정보(유실·중복, 권한, 콘텐츠 유출, PDPA) ③ 앱 UI/UX·9개 언어(웹 화면을 PC·폰 폭으로 띄운 스크린샷, 번역 누락, 브랜드 가이드, 한국어 문구 톤) ④ 운영·인프라·문서(데모 서버, 배포 워크플로, Sentry 새 오류, 비용, STATUS와 코드가 맞는지). 타입·린트·테스트·의존성 취약점은 매번 공통으로 봐요.

무엇을 바로 고쳐서 올리나?

버그·보안 구멍·데이터 오류처럼 반드시 고쳐야 하는 것은 묻지 않고 고칩니다. 로컬 검사가 통과하면 main에 합쳐 데모(프리뷰)에 배포하고, 배포 뒤 자동 점검 결과까지 확인합니다. 데모 새벽 초기화나 소속사 미팅 직전처럼 배포를 피할 시간에는 올리지 않고 다음 가능한 시간에 올려요.

무엇을 물어보나?

기능 동작이 바뀌는 기획 결정, 가격·정산 비율·환불 정책, 되돌리기 어려운 스키마 대공사, 돈이 드는 외부 서비스, 스토어 심사가 필요한 새 빌드가 해당됩니다. 이런 건 "결정 필요"로 표에 올리고 추천안을 함께 적습니다. 화면이 크게 바뀌는 UI/UX 제안도 여기로 와요.

문구 톤은 어떻게 보나?

한국어 문장이 전부 "~요"로 끝나면 AI가 쓴 글처럼 보입니다. 그래서 설명·정책·주의사항은 "~합니다"를 기본으로 하고, 사용자에게 건네는 짧은 말에는 "~해요"를 섞어 씁니다. 같은 어미가 세 번 연달아 나오지 않게 하는 게 기준이에요. 자세한 기준은 docs/product/brand-guide.md "문구 톤"에 있습니다.

운영(실제 사용자) 서버는?

운영 환경이 아직 없어서 지금은 데모(프리뷰)까지만 올립니다. 운영이 생기면 운영 배포 워크플로가 GitHub 승인을 요구하므로, 그때 자동 반영 범위를 다시 정해요.

기록은 어디에 남나?

할 일 목록의 원본은 이 보드입니다. 저장소에는 회차마다 작업 로그(docs/deployment-readiness-plan.md)에 한 단락을 남기고, 상태가 바뀐 기능은 STATUS.md에 반영합니다. 폰에서 확인해야 하는 화면은 실기기 테스트 페이지에 넣어 둘게요.
