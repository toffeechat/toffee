2026-10-25 사용자 질문("3만 명이 메시지 100개를 보낼 수도, 50만 개를 보낼 수도 있는데 정말 버티나? 부하 테스트는 꼭 하고 잊지 않게
기록해 달라")에서 정리. **언제**: 운영 서버·DB를 Railway에 만든 직후, 스토어 제출 전(사업 본부 "운영 전환" 단계 중 운영 서버를 연 뒤,
`launch-roadmap.md` 6단계 체크박스, 사업 본부 할 일 `s3-load`). 운영 DB에 가짜 데이터를 넣지 않도록 **운영과 같은 사양으로 만든
임시 Railway 프로젝트**에서 하고 끝나면 지운다.

## 아직 확인하지 않은 것 — 이번에 꼭 잴 것

구조상 유리한 점: 아티스트 메시지는 구독자가 몇 명이든 **DB에 한 줄**(버블 방식, 볼 때 이름만 바꿈), 사진·영상은 서버를 거치지 않고
R2로 직접, 푸시는 FCM이 500건씩 묶어서 보냄, 팬 답장은 **아티스트 메시지 하나당 팬 1명 3개까지**(`FAN_REPLIES_PER_MESSAGE`)이고 다른
팬에게는 신호가 가지 않음. 그래서 "메시지 총개수"보다 **짧은 시간에 몰리는 요청 수**가 관건이다. 지난 테스트는 "보내기 → 신호 도착"만
쟀고, 아래 상황은 안 쟀다.

| # | 상황 | 왜 위험한가 | 재는 것 | 합격 기준(잠정) |
|---|---|---|---|---|
| 1 | **푸시 직후 앱 열기 폭주** — 구독자 3만 명 방에 메시지 1개, 1분 안에 30%(9,000명)가 앱을 열어 대화방·인박스를 받음 | 한 명이 3~5개 요청 → 1분에 3만~4.5만 요청(초당 500~750). 지난 테스트에 없던 **읽기 폭주** | 요청 응답 시간 p95·오류율, DB CPU, DB 연결 대기 | p95 1초 이하, 오류 0.1% 이하 |
| 2 | **팬 답장 폭주** — 같은 메시지에 1분 안에 1만 명이 답장 | 답장 1개 = 계정 확인·횟수 확인·저장·신호 등 DB 작업 4~6번 | 위와 같음 + 저장 실패 0건 | 답장 유실 0, p95 2초 이하 |
| 3 | **아티스트·소속사 화면에 답장 신호 폭주** | 답장마다 `fan-reply` 신호 → 앱이 답장 목록을 다시 받음(`app/src/lib/realtime.ts`). 1만 개면 아티스트 폰·소속사 PC가 1만 번 새로고침 시도 | 아티스트 화면 요청 수·버벅임 | 묶어서 새로고침(예: 2초에 1번)이 필요하면 고친다 |
| 4 | **실시간 연결 1만~3만 개** | 지난 테스트는 3,000개. 연결 하나당 메모리 약 0.1MB | 메모리·연결 열리는 시간 | 1GB 서버에서 몇 개까지인지 숫자로 기록 → 증설 기준 갱신 |
| 5 | **메시지가 쌓인 DB** — 아티스트 메시지 수만 개·팬 답장 수백만 개 | 목록·검색·통계 쿼리가 느려질 수 있음(방 안 검색은 `pg_trgm` 검토 메모 있음) | 주요 화면 응답 시간 | p95 0.5초 이하 |
| 6 | **아티스트 여러 명이 동시에 발송** — 예: 10명이 같은 시각 | 푸시 대상 조회·FCM 호출이 겹침 | 발송 API·푸시 도착 | 발송 API 1초 이하 |
| 7 | **서버 2대** | 증설 때 신호가 모든 서버에 가는지(Postgres LISTEN/NOTIFY) | 2대에서 #1·#2 다시 | 신호 유실 0 |

## 미리 볼 설정값

- **DB 연결 수**: 서버 1대당 `DB_POOL_MAX`(기본 10). #1·#2에서 요청이 "DB 연결 기다림"으로 밀리면 올리되, Railway Postgres 최대 연결 수
  (서버 대수 × 풀 + LISTEN 연결 1개씩)를 넘지 않게.
- **요청 횟수 제한**: `ThrottlerModule` IP당 1분 60회. 부하 테스트 도구가 한 IP에서 보내면 여기서 막히니, 테스트 서버에서만 올리거나
  여러 계정·IP로 나눠서. 실제 운영에선 통신사 공유 IP(태국 모바일)로 여러 팬이 한 IP에 묶일 수 있는지도 같이 확인.
- **호스팅 연결 시간 제한**: SSE는 오래 열려 있는 연결 — Railway의 연결 유지 한도.
